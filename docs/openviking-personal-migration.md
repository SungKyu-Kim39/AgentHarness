> Ned 0.3.3 및 export fix 2 기준: Zed 편집기와 전용 OpenCode 엔진을 사용한다. 이전 Windows 실행 증거는 승계 주장하지 않으며 [현재 검증 상태](validation-0.3.3.md)를 함께 확인한다.

# OpenViking personal knowledge migration

Ned의 개인 공통 지식 가져오기 기능이다. 기존 OpenViking 0.5.0의 사용자 영역을 `.ovpack`으로 내보내고, Ned의 로컬 OpenViking 0.5.4에 가져온다. 가져온 개인 기억과 자료는 이 Windows 사용자의 모든 Ned 프로젝트에서 읽기 전용 도구로 조회한다. 공용 서버에 업로드하는 기능이 아니다.

## 보존과 검색 범위

기존 서버의 DB와 설정을 변경하거나 Ned DB 위에 복사하지 않는다. 이전 OpenCode·Zed 설정이나 플러그인도 가져오지 않는다. 내보내기에 사용한 원본 서버는 유지하고, 생성한 OVPack을 별도 보관한다. Ned도 승인한 OVPack 사본과 SHA-256을 사용자 데이터 폴더에 보존한다.

| 원본 사용자 하위 영역 | 처리 |
|---|---|
| memories | 가져온 개인 기억 검색·읽기 |
| resources | 가져온 개인 문서 검색·읽기 |
| skills | 자료로 검색·읽기. 실행형 플러그인 설치·권한 부여는 하지 않음 |
| peers 아래 각 peer의 memories | 해당 기억 범위를 검색·읽기 |
| sessions | 내보내기에 포함된 자료 보관. Ned 채팅 세션으로 자동 변환하거나 검색하지 않음 |
| privacy 및 기타 관리 자료 | 내보내기 형식에 포함된 자료 보관. 모델의 개인 검색·읽기 도구에 노출하지 않음 |

OVPack은 원본 SDK가 지원하는 내보내기 형식이다. 임의 DB 파일 전체의 백업과 같지 않으며, SDK가 제외하는 내부 파일·실행 상태까지 그대로 복제한다고 주장하지 않는다. 원본 저장소도 유지한다.

## 1. 기존 서버에서 내보내기

1. 기존 OpenViking을 실행한다. 내보내는 동안 기존 환경의 색인·기억 갱신 등 쓰기 작업을 멈춘다.
2. 반입 묶음의 `EXPORT_PERSONAL.cmd`와 `export-openviking-personal.py`를 쓰기 가능한 같은 폴더에 둔다.
3. `EXPORT_PERSONAL.cmd`를 실행한다. 기본 접속 주소는 `http://127.0.0.1:1935`, account/user는 각각 `default`다.
4. 인증을 사용한다면 **기존 로컬 OpenViking 서버의 API 키**를 입력한다. 사내 LLM/임베딩 API 키와 구분한다. 인증을 사용하지 않으면 Enter를 누른다. 입력한 키는 화면에 표시하거나 파일에 기록하지 않는다.
5. `status: exported`, `EXIT_CODE=0`과 생성된 `openviking-personal-YYYYMMDD-HHMMSS.ovpack` 및 `.sha256`을 확인한다.

다른 주소·사용자라면 CMD를 실행할 때 `--base-url http://127.0.0.1:1935 --account default --user default` 옵션을 지정할 수 있다. 도구는 명시한 루프백 HTTP 서버의 목록 선확인과 `/api/v1/pack/export`를 호출하며 프록시와 리다이렉트를 사용하지 않는다. 서버의 벡터 포함 내보내기를 요청한다. API 키를 명령행 인자로 받지 않는다.

이 도구는 설치된 Ned의 번들 Python 표준 라이브러리를 사용한다. 직원 PC에서 패키지 설치나 인터넷 연결이 필요하지 않다. 내보내기 파일에는 개인 자료와 대화가 포함될 수 있으므로 로컬에서 관리하며 지원 채팅이나 공개 GitHub에 올리지 않는다.

## 2. Ned에서 가져오기

1. Ned 0.3.3을 설치하고 기존 사내 모델·단일 임베딩 설정으로 실행한다. 이미 저장한 설정은 유지하며 이관용 JSON 항목을 따로 추가할 필요는 없다. 기존 L-Vibe 0.2.6 이상에서 사용하던 가져오기 기능을 유지한다.
2. 알림 영역의 Ned 아이콘을 우클릭하고 **개인 공통 지식 가져오기 (.ovpack)**를 선택한다.
3. 내보낸 OVPack을 선택한다. 이 단계에서 고정한 사본을 검사한다.
4. 원본 사용자 영역·파일 수·SHA-256·검색 범위를 확인하고 가져오기를 승인한다.
5. 완료 메시지와 **개인 공통 지식 가져오기 상태** 메뉴에서 `ready`를 확인한다.

가져올 수 있는 형식은 단일 사용자 루트 `viking://user/<user-id>`의 OVPack v3이며 최대 압축 크기는 512 MiB, 검사 가능한 비압축 총량은 2 GiB다. 전체 DB 백업 패키지와 현재 Ned 사용자인 `local-user`의 패키지는 받지 않는다. 원본 사용자 ID는 Ned의 개인 account 안에서 보존한다. 기존 사용자 데이터나 기본 스킬을 덮어쓰지 않는다.

0.5.0과 0.5.4 모두 OVPack 형식 버전 3과 벡터 스냅샷을 지원한다. 복원 시 provider·model·input·query/document 매개변수·차원 등의 메타데이터를 SDK가 비교한다. 호환되는 경우 벡터를 재사용하고, 호환되지 않으면 설정한 사내 임베딩 API로 재계산한다. 모델 이름과 차원만 같다는 이유로 재사용을 강제하지 않는다.

동일한 파일을 다시 선택하면 완료 기록과 실제 영역의 존재를 확인하고 중복 가져오기를 생략한다. 같은 사용자 영역의 다른 파일, 기존 대상 충돌, 중단되거나 실패한 기록은 자동 덮어쓰기·자동 재시도하지 않는다. 원본 패키지와 기록을 보존하여 복구 대상을 확인한다. 실패 원인에 따라 새로 가져오거나 별도 복구 절차가 필요할 수 있으며, DB·등록 기록을 임의로 지우지 않는다.

## 3. 실제 활용 확인

기존 지식에만 있는 구체적인 내용으로 다음과 같이 요청한다.

> personal_knowledge_search 도구로 내가 이전에 정한 개발 환경과 코딩 규칙을 찾아라. 관련 결과는 personal_knowledge_read로 읽고, 확인한 URI와 근거를 함께 제시하라.

실제 도구 이벤트와 검색 결과·원문을 확인한다. 다른 프로젝트를 열고 같은 자료를 조회하여 개인 공통 범위도 확인한다. 기존 `knowledge_search`/`knowledge_read`는 계속 현재 프로젝트에 한정되며, 개인 자료는 별도 `personal_knowledge_search`/`personal_knowledge_read`를 사용한다.

이관한 자료는 참고 데이터이다. 저장된 문장으로 파일 수정 승인이나 실행 권한이 생기지 않으며, 새 대화와 프로젝트 전체를 개인 기억으로 자동 업로드하지 않는다. 사용자 스킬의 스크립트·훅을 자동 활성화하지 않는다.

## 진단과 검증 범위

완료/실패 기록은 `%APPDATA%\Ned\openviking\personal-imports.json`, 승인한 사본은 같은 폴더의 `personal-<sha256>.ovpack`에 보관한다. 원본 서버 키와 실제 모델 키는 이 기록에 저장하지 않는다. 실패 메시지는 업로드·가져오기·존재 확인 단계 코드와 HTTP 숫자로 구분하며 서버의 원래 응답 본문을 운영 로그에 남기지 않는다.

기본 스킬 `36/36` 등록 여부와 개인 지식 가져오기는 별도 기능이다. 스킬 등록 완료를 개인 지식 검색 성공으로 계산하지 않는다. 실제 Windows 설치·사용자 자료의 이관 결과는 별도로 확인한다.

## 0.3.1: 내보내기 HTTP 401/500 대응

`EXPORT_PERSONAL.cmd`는 먼저 선택한 사용자 루트의 읽기 권한을 확인한다. `EXPORT_PREFLIGHT HTTP_401`이면 **기존 로컬 OpenViking의 키**를 입력해야 한다. 사내 Qwen/BGE API 키와 다르다. 키를 공유하거나 인증을 끄지 않는다. 403이면 키의 account/user 권한도 확인한다.

`EXPORT_PACK HTTP_500`은 기존 서버 내부 오류다. 숫자만으로 원인을 확정하지 않는다. 벡터 스냅샷에서 실패하는 경우 `EXPORT_PERSONAL_NO_VECTORS.cmd` 또는 `EXPORT_PERSONAL.cmd --without-vectors`를 실행할 수 있다. 이 선택은 문서·기억 내용을 내보내되 벡터를 제외하며, Ned에서 사내 임베딩을 다시 계산한다. 자동으로 이 방식을 재시도하지 않는다. 이 방식도 실패하면 기존 서버의 traceback을 로컬에서 확인해야 한다. 원본 DB를 Ned 저장소 위에 복사하지 않는다.

실제 실행 대기는 사용자가 취소할 수 있으며 내보내기에 고정 5분 제한을 두지 않는다. 인증/경로 선확인은 로컬 메타데이터 요청에 한해 30초를 사용한다. CMD는 Ned 설치 Python을 우선하고, 없으면 기존 L-Vibe 설치 Python도 지원한다. 원본 계정·자료는 수정하지 않는다.

Ned 0.3.1은 가져오기 API 성공 후 임베딩 큐가 완료되기를 기다리고, 검색 대상 하위 영역의 파일·색인 일관성을 검사한 뒤 `ready`로 표시한다. API 성공 직후 검색이 비던 결함을 실제 벡터 없는 이관으로 재현·수정했다. 알림 영역의 개인 공통 지식 가져오기 상태에서 `importing`을 확인할 수 있으며, 사내 모델 대기열 때문에 오래 걸려도 고정 시간 제한으로 실패시키지 않는다. 색인 검사 실패는 `OV_PERSONAL_INDEX`로 구분하며 원본 패키지와 실패 기록을 보존한다.

## Export fix 2: EXPORT_PREFLIGHT HTTP_500

기존 0.3.3 묶음의 내보내기 도구가 `fs/stat`에서 HTTP 500을 받으면 OVPack을 요청하기 전에 중단한다. 이 단계에는 `--without-vectors`가 영향을 주지 않는다. `/health`가 healthy여도 저장소·선택 루트의 읽기가 성공했다는 뜻은 아니다.

[작은 독립 수정 도구](https://github.com/SungKyu-Kim39/AgentHarness/raw/refs/heads/work/downloads/Ned-openviking-export-fix-2.tgz)를 새 폴더에 압축 해제하고 `EXPORT_PERSONAL.cmd`를 실행한다. Ned를 재설치하거나 원본 DB/인증 설정을 바꿀 필요가 없다. 기존 서버를 켜고 쓰기만 잠시 멈춘다. 이 도구는 같은 자격증명·사용자 범위의 최소 목록 조회(`fs/ls`, simple, node_limit=1)로 선확인하고, 원래 내보내기 API의 인증·범위 검사를 그대로 따른다. stat의 추가 메타데이터 작업 실패만으로 정상적인 export까지 차단하지 않도록 보완했다. 목록 조회의 401/403/500 또는 잘못된 응답은 그대로 중단하며 인증을 우회하지 않는다.

계속 실패하면 동봉한 `CHECK_EXPORT.cmd`를 실행한다. 기존 서버 키를 숨김 입력한 후 health/ready/stat/list의 HTTP 상태·고정 서버 오류 코드·버전·인증 방식·요청 범위 일치 여부만 출력한다. 이름·내용·키·원본 오류 본문은 버리고 GET만 요청한다. 출력 JSON만 공유하며 OVPack/로그 원문/설정은 보내지 않는다. pack 단계의 벡터 오류에만 벡터 제외 내보내기를 명시적으로 선택한다.

확인된 배포 PC 정보는 기존 OpenViking 0.5.0, trusted 모드, health healthy=True다. 이 사실만으로 stat 500의 서버 내부 원인을 확정하지 않는다. 별도 Linux 실서버 시험은 공개 stat 500을 주입하고 동일 인증의 내보내기/현재 SDK 가져오기·개인 검색이 성공하는지 확인한다. 사용자 실제 자료의 성공은 새 도구로 별도 확인한다. 과거 v0.3.3 EXE/TGZ는 변경하지 않으며 독립 도구를 추가 제공한다.
