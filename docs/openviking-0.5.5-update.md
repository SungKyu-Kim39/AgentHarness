# OpenViking 0.5.5 업데이트와 Ned 저장소 이름 이관

Ned 0.3.7 수정 빌드 1은 OpenViking을 0.5.4에서 0.5.5로 업데이트하고, 새 저장소와 기본 스킬에 사용하던 이전 제품 이름을 `ned`로 바꿉니다. 기존 자료는 보관한 뒤 파일과 검색 인덱스를 함께 이관합니다. 원본 0.3.7 EXE·TGZ와 태그는 그대로 보존하며, 수정 파일은 `0.3.7-rebuild1`로 구분합니다.

## 어떤 이름이 바뀌나

이전 구현에는 화면과 도구 이름을 Ned로 바꾼 뒤에도 OpenViking의 내부 계정과 스킬 등록 이름이 남아 있었습니다. 폴더를 사용자가 직접 만든 것이 아니라 앱이 이전 이름으로 계속 등록하던 문제입니다.

| 항목 | 기존 구현 | 수정 후 새로 사용하는 값 |
| --- | --- | --- |
| OpenViking 계정 | `l-vibe` | `ned` |
| 기본 스킬 이름 | `l-vibe-<스킬 ID>` | `ned-<스킬 ID>` |
| 스킬의 번들 정보 파일 | `L-VIBE-BUNDLE.json` | `NED-BUNDLE.json` |
| 스킬 소유·무결성 메타데이터 | `l_vibe_*` 필드 | `ned_*` 필드 |
| 프로젝트 지식 URI | `viking://resources/l-vibe/<프로젝트 ID>` | `viking://resources/ned/<프로젝트 ID>` |
| 현재 빌드의 OpenCode 소스 캐시 | `.cache/l-vibe-desktop/source` | `.cache/opencode/source` |

이관 후 기본 스킬의 활성 저장 위치는 다음과 같습니다.

```text
%APPDATA%\Ned\openviking\data\viking\ned\agent\skills\ned-<스킬 ID>
```

현재 Ned 설치 리소스는 `resources/ned`만 사용합니다. 모델이 읽는 기본 스킬 ID 66개와 도구의 `ned_host_*` 이름은 유지합니다. 다른 프로젝트·모델의 고유 이름이나 사용자가 작성한 문서 본문은 일괄 치환하지 않습니다.

## 기존 PC에서는 어떻게 옮기나

업데이트 전 진행 중인 작업을 마치고 Ned를 완전히 종료합니다. 수정 빌드를 설치한 뒤 실행하면 이전 OpenViking 계정이 있는지 확인합니다. 설정 JSON이나 임베딩 모델을 새로 작성할 필요는 없습니다.

이관은 다음 순서로 진행합니다.

1. 원래 저장소의 사본을 비공개 백업 폴더에 만듭니다. 새 SDK는 유일한 원본 대신 이 사본을 엽니다.
2. OpenViking API로 프로젝트·사용자 자료를 내보냅니다. 호환되는 벡터도 함께 내보내며, 원본 인덱스가 불완전하면 파일을 보존해 새 저장소에서 인덱스를 재구성합니다.
3. SDK 백업에 포함되지 않는 `agent` 영역은 서비스가 멈춘 상태에서 별도로 복사합니다. 기본 스킬 외의 사용자 자료도 보관합니다.
4. 빈 임시 저장소의 `ned` 계정으로 복원합니다. 프로젝트 지식과 앱 소유 기본 스킬의 경로를 SDK로 옮기고, 필요한 인덱스를 다시 만듭니다.
5. 자료와 인덱스의 일관성, 스킬 원문·참조 파일을 확인합니다. SDK가 다시 만드는 요약의 변화와 사용자가 수정한 원문을 구분합니다.
6. 서비스를 종료한 뒤 검증한 저장소를 활성 `data` 경로로 전환합니다. 원래 저장소는 백업에 남기고 이후에는 새 이름으로 등록합니다.

일반 에이전트 대화에는 기존 사용자 범위를 계속 적용합니다. 계정 유지보수 권한은 엔진과 도구가 준비되기 전, 이관용 비공개 로컬 연결에서만 사용합니다. 모델이나 스킬에 관리자 권한을 주는 변경은 아닙니다.

첫 실행은 평소보다 오래 걸릴 수 있습니다. 다시 색인할 자료가 많거나 사내 모델 대기열이 길면 그 처리를 기다립니다. 모델 생성 대기에 기본 시간 제한을 추가하지 않습니다. 반복 실행하기보다 시작 상태를 확인하고, 중단해야 한다면 Ned를 정상 종료해 주세요. 완료한 이관은 재실행하지 않습니다.

## 실패하거나 수정한 사본이 있으면

복원·검증 단계에서 실패하면 원본 저장소를 활성 경로에 유지하고 실패한 임시 사본을 보관합니다. 이름이 겹치는 대상 계정이 이미 있으면 자동으로 합치거나 덮어쓰지 않습니다. 저장소 전환 중 중단된 경우에는 기록된 전환 상태를 확인해 복구하며, 확인할 수 없는 상태를 완료로 표시하지 않습니다.

사용자가 수정한 기본 스킬은 원문을 덮어쓰지 않고 충돌로 알립니다. SDK가 만든 요약만 달라진 정상 이관은 소유·무결성 기록과 대조해 처리합니다. 출처를 확인할 수 없는 사용자 스킬도 임의로 앱 기본 스킬로 취급하지 않습니다.

확인할 파일과 폴더는 다음과 같습니다.

- `%APPDATA%\Ned\openviking\namespace-migration.json`: 이관 단계와 완료 상태입니다.
- `%APPDATA%\Ned\openviking\namespace-backups\<이관 ID>`: 원본 저장소, 읽기 사본, SDK 내보내기와 스킬 등록 기록을 보관합니다. 실패한 시도의 임시 저장소도 남을 수 있습니다.
- `%APPDATA%\Ned\openviking\startup-status.json`: 시작 실패의 고정 코드와 종료 확인 상태입니다. 이름 이관 실패는 `OV_NAMESPACE`로 구분합니다.
- `%APPDATA%\Ned\openviking\skills-status.json`: 기본 스킬 등록 상태와 충돌·실패 항목입니다.

백업에는 개인 자료가 들어 있으므로 지원 채팅이나 공개 GitHub에 올리지 마세요. 이관을 위해 원본과 임시 사본을 보관할 여유 공간도 필요합니다. 활성 폴더의 이름이나 DB 내부 파일을 탐색기에서 직접 바꾸지 마세요.

## 0.5.5 번들에서 바뀌는 구성

OpenViking 0.5.5의 고정 Windows x64 wheel과 대응 소스를 포함합니다. 새 버전의 의존성 조건에 맞춰 LiteLLM을 1.102.4에서 1.103.10으로 바꾸고, 기존 Windows Python 패키지 344개의 버전 조건을 다시 대조했습니다. 다른 패키지를 `latest`로 일괄 갱신하지 않습니다.

순수 Python SDK의 ZIP 배치, 정적 토크나이저 자료, 앱 전용 실행·종료와 외부 연결 제한은 유지합니다. 직원 PC에서 pip 설치나 첫 다운로드를 수행하지 않습니다. 대응 소스와 라이선스는 반입 TGZ의 `source/`에 함께 제공합니다.

확인한 버전·파일 해시는 [업그레이드 잠금 파일](../openviking-upgrade-lock.json), [Windows Python 잠금 파일](../python-runtime-lock.json), [설치 최적화 잠금 파일](../release-runtime-lock.json)에 기록합니다. Linux의 실제 SDK 검사, Windows 번들 검사와 실제 직원 PC의 사내 모델·화면 검증은 각각 구분합니다.

## 이전 이름이 기록에 남는 경우

이미 게시한 과거 배포 파일·해시·검증 기록은 당시 대상을 식별할 수 있도록 보존합니다. 이관 코드에도 이전 계정·파일·메타데이터를 찾아 읽기 위한 식별자가 필요합니다. 복구용 원본 사본과 사용자 작성 자료에도 이전 이름이 남을 수 있습니다. 이를 지우기 위해 과거 기록이나 개인 자료를 다시 쓰지는 않습니다.

이번 수정의 기준은 **현재 앱이 새로 만드는 계정·스킬·메타데이터·프로젝트 지식 경로에는 Ned 이름을 사용하고, 기존 자료를 검증해 새 활성 경로로 옮기는 것**입니다. 실제 기본 스킬 등록과 자료 검색을 각각 확인한 뒤 사용해 주세요.
