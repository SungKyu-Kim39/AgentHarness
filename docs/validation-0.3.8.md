# Ned 0.3.8 검증 기록

0.3.8은 대화 요약의 출력 한도 처리, 알림 영역의 OpenViking Studio 실행, 새 스킬·MCP 확장 안내를 추가합니다. 기존 설정·지식·대화·편집기 환경은 보존하며, OpenViking 0.5.5와 기본 스킬 66개를 유지합니다. 과거 설치 파일과 태그는 덮어쓰지 않습니다.

## 요약 실패의 근거와 수정

고정 OpenCode 소스의 compaction 처리에서 `finish_reason: length`를 `Compaction summary reached the output token limit` 오류로 바꾸는 경로를 확인했습니다. 실제 고정 엔진의 로컬 요청에서도 요약에 일반 도구 정의가 포함되는 것을 확인했습니다. 실제 사내 Qwen 서버의 토큰 한도·thinking 구현을 별도로 관찰한 것은 아니므로, 그 서버의 단일 원인을 확정하지 않습니다.

0.3.8은 엔진의 마지막 요약 지시를 식별해 도구 정의를 제거하고 간결한 요약을 요청합니다. Qwen의 요약에는 기본적으로 thinking off 옵션을 사용합니다. 엔진이 계산한 출력 여유와 모델·요약 설정의 상한을 넘기지 않습니다. `length` 응답은 보류하고 한 번만 더 짧게 요청합니다. 완료된 응답만 엔진에 전달하며, 두 번째도 잘리면 재시도 대상 HTTP 오류로 위장하지 않고 고정 코드와 422를 돌려줍니다. 서버가 보고한 사용량은 합산하고, 기존 대화와 일반 요청의 thinking·대기 정책은 유지합니다.

실제 엔진과 localhost 합성 모델로 첫 요약을 강제로 자른 뒤 두 번째 완성된 요약만 완료 상태로 저장하는 검사를 실행했습니다. 게이트웨이에서는 반복 실패·재요약 해제·일반 요청 보존·usage 합산·미완료/도구 호출 응답 거절을 검사합니다. [원인·설정·대응 안내](compaction-troubleshooting.md)를 함께 제공합니다.

## Studio와 확장 안내

알림 영역의 **OpenViking Studio 열기**는 Ned가 실행한 로컬 서버의 `/studio/`를 별도 격리 창에서 엽니다. 실행별 인증은 호스트 요청 헤더에만 넣습니다. 창은 Node·팝업·외부 접속·임의 MCP와 서버 설정 변경에 접근하지 못하며, 사람이 직접 관리하는 `ned` 계정 범위는 모델 도구에 전달하지 않습니다. 서비스 종료·설정 재시작 시 창을 닫고 준비 중 종료나 중복 클릭도 처리합니다.

실제 OpenViking 0.5.5 Studio SPA는 격리된 Chromium에서 로컬 인증과 CSP를 적용해 렌더링했습니다. 창 정책과 수명 검사는 실제 Studio 클래스를 번들한 테스트에서 실행했습니다. 이는 실제 Windows 트레이·GPU·파일 선택 UI 검증과 별도입니다.

[확장 안내](extension-guide.md)는 사용자가 바로 둘 수 있는 프로젝트 지침, 배포 담당자의 기본 스킬 추가, 실행형 MCP의 검토·번들·권한·검증 절차를 구분합니다. 임의 MCP 설치 메뉴가 있는 것처럼 설명하지 않습니다. [Studio 안내](openviking-studio.md)도 제공합니다. 세 문서는 반입 TGZ와 설치된 안내 자료에 포함합니다.

## 배포와 검증 범위

기존 고정 기준 설치본의 런타임을 해시로 확인하고 OpenViking 0.5.5의 검토된 Windows 런타임과 무손실 SDK ZIP 배치를 유지합니다. 호스트·ACP는 이번 소스에서 다시 빌드하며, 추출 파일 전체와 manifest를 대조합니다. 설치본의 실제 소스 커밋·SHA-256·파일 수는 `INSTALLER_AUDIT.json`, `PAYLOAD_MANIFEST.json`과 저장소의 `downloads/Ned-0.3.8-*` 기록에 남깁니다.

TypeScript·기본 스킬·전체 회귀 검사와 Windows 설치·실제 엔진 요약·SDK 이관 결과는 해당 버전의 기록을 기준으로 확인합니다. 설치 파일을 만든 뒤 완료한 공개 다운로드·Windows 검증은 저장소의 후속 기록으로 제공합니다. 실제 직원용 Windows 10·11 GUI, 사내 Qwen/BGE의 긴 대기열과 전체 런타임 DNS·TCP 관찰은 별도 수용 범위이며 `releaseReady`는 false로 유지합니다.

## 개인 지식 가져오기 복구

0.3.7은 같은 SHA-256 또는 사용자 영역에 실패 기록이 있으면 가져오기를 항상 차단했습니다. 파일 수만으로 가져오기가 완료됐다고 판정할 수 없어 실패 기록을 삭제하는 방식으로 고치지 않았습니다. 완료 증거가 없는 대상은 새 `ned-import-<식별자>` 영역에 SDK로 검증한 패키지를 가져오고, 이전 실패 영역·등록 기록·원본 패키지는 보존합니다. 파일 내용은 그대로 유지하고 사용자 경로에 종속된 벡터를 재계산합니다. SDK 가져오기 완료 기록이 있는 재시도는 복사 없이 색인만 복구합니다.

실제 0.5.0 서버가 내보낸 벡터 패키지를 0.5.5로 가져온 뒤, 0.3.7 형태의 실패 기록을 만들어 같은 파일로 복구했습니다. 원본 파일 바이트·실패 행이 남고 새 영역을 개인 도구로 읽고 검색할 수 있음을 확인했습니다. 다음 재시도는 완료 확인과 색인 복구만 수행했습니다. 별도 합성 OVPack 13,242개 파일은 SDK 검사·사용자 영역 변환 뒤 전체 내용이 일치했고, 변조한 파일은 출력 생성 전에 거절했습니다. 실제 사용자 패키지의 모든 임베딩을 완료했다고 주장하지 않습니다.

## Git·Ghidra·외부 읽기

Git은 고정 portable Git의 plumbing 명령으로 선택한 파일만 스테이징·커밋합니다. 기존 index의 다른 스테이징, 작업 파일의 이후 수정, 삭제·초기 커밋, 작성자 부재, 승인 거절, 외부 index.lock 보존, 승인 후 입력 충돌을 실제 Git에서 검사했습니다. hooks·서명·외부 필터·원격 통신은 실행하지 않습니다. 실제 commit 해시와 저장된 blob을 대조했습니다.

REA 6.8.0의 원본 Ghidra 연동은 12.1.4를 검증 버전으로 명시하지만 기존 Ned에는 Ghidra·Java 실행기가 없었습니다. 12.1.4와 Temurin JDK 21.0.13+9를 해시로 고정하고 Java 21 전용 루프백 네트워크 가드를 추가했습니다. 원본 REA 파일은 보존하며 고정 소스 해시를 검사하는 메모리 어댑터로 가드를 전달합니다. 실제 REA/Ghidra는 합성 PE의 함수와 의사코드를 반환했고 대상 파일을 실행·수정하지 않았습니다. 실제 Java는 루프백 TCP 통신을 허용하면서 외부 DNS·소켓 및 가드 해제를 거절했습니다.

전체 권한의 외부 읽기는 명시한 로컬 텍스트·폴더에 한합니다. 권한 해제·취소·앱 관리 자격증명·네트워크 경로·바이너리 거절을 검사합니다. 외부 쓰기 권한은 추가하지 않습니다. [사용 안내](git-and-binary-analysis.md)에 범위와 예시를 적었습니다.

## 빌드 전 Linux 회귀 검사

`npm run typecheck`, `npm run skills:verify`(66개), `ELECTRON_BUILDER_CACHE="$PWD/.cache/ned/builder-cache" npm test`를 실행했습니다. 전체 185개 중 176개 통과, 9개 환경별 건너뜀, 실패 0개입니다(약 690초). Ghidra를 별도 회귀 검사와 동시에 실행한 중간 시험에서는 Linux 프로세스 소유권 검사에서 다른 sandbox 프로세스의 `/proc` 접근 거절을 보존했고, 검사 완화 없이 전체 실행의 실제 REA/Ghidra 시험이 통과했습니다. Windows 실행과 직원 PC 검증은 이 결과와 구분합니다.
