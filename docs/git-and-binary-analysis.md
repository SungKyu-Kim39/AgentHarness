# Git 커밋과 Ghidra 바이너리 분석

Ned 0.3.8은 Git 스테이징·커밋과 REA의 Ghidra 분석을 호스트 도구로 제공합니다. 모델이 명령어를 안내하는 데 그치지 않고, 번들 실행기로 작업한 결과를 돌려줍니다. 인터넷 연결이나 별도 Java 설치가 필요하지 않습니다.

## 변경 파일 커밋하기

프로젝트 루트에 일반 `.git` 디렉터리가 있어야 합니다. 다음처럼 요청할 수 있습니다.

> 변경 내용을 확인하고, 이번에 수정한 `src/example.cpp`와 `README.md`만 스테이징한 뒤 적절한 메시지로 커밋해 주세요. 다른 사람이 스테이징한 파일은 그대로 두세요.

에이전트는 `ned_host_git_inspect`로 변경을 조회하고 `ned_host_git_stage`, `ned_host_git_commit`을 실행합니다. 결과의 `commit` 값이 실제 로컬 커밋 해시입니다. 계획이나 커밋 메시지 제안만 출력한 것은 커밋 완료가 아닙니다. 원격 푸시는 지원하지 않습니다.

커밋에는 **지정한 경로의 스테이징된 내용만** 들어갑니다. 다른 파일의 스테이징과 스테이징 이후 작업 파일에 추가한 수정은 유지합니다. 스테이징 승인 뒤 파일이 바뀌거나, 커밋 승인 뒤 브랜치·HEAD·index가 바뀌면 중단하고 다시 확인합니다. 같은 파일을 외부 편집기에서 수정했다면 저장한 뒤 요청하세요.

작성자는 저장소 로컬의 `user.name`, `user.email` 또는 사용자가 직접 제공한 이름·이메일을 사용합니다. 개인 전역 Git 설정을 복사하거나 작성자를 임의로 만들지 않습니다. 정보가 없으면 “작성자는 홍길동, 이메일은 hong@example.com으로 이번 커밋에 사용해 주세요”처럼 알려줄 수 있습니다. 이 값으로 전역 설정을 바꾸지는 않습니다.

`승인 요청`과 `프로젝트 파일 자동 승인` 모드에서는 Git 쓰기 승인을 확인합니다. `전체 권한`에서는 지원하는 Git 스테이징·커밋의 승인창을 생략합니다. 파일 수정 자동 승인만으로 명령 실행까지 허용되는 것은 아닙니다.

### 지원 범위

- 추가·수정·추적 파일 삭제를 경로별로 스테이징합니다. 한 번에 최대 100개 경로, 파일당 최대 64 MiB입니다.
- 스테이징은 승인한 파일 바이트를 그대로 사용합니다. 외부 clean/LFS 필터와 자동 줄바꿈 변환은 실행하지 않습니다. CRLF/LF를 의도대로 저장한 뒤 요청하세요.
- hooks·서명·외부 필터·원격 통신을 실행하지 않습니다. hooks나 서명이 필수인 팀의 최종 커밋 절차는 기존 개발 도구를 사용하세요.
- 연결된 worktree·submodule, shallow 저장소, detached HEAD, 충돌·병합·rebase 진행 중인 저장소, 외부 include 설정은 지원하지 않습니다. 이런 상태에서는 구체적인 오류를 표시하며 자동 복구하지 않습니다.

## Ghidra로 EXE·DLL·펌웨어 조사하기

REA는 여러 역공학 도구를 연결하는 분석 계층입니다. Ghidra는 실행 파일의 기계어에서 함수·호출 관계를 찾고 C와 비슷한 의사코드를 만드는 도구입니다. 기존 Ned의 `rea_inspect`는 Go·Rust·Python 바이트코드 등의 형식별 정적 검사만 제공했습니다. 0.3.8의 `rea_ghidra`는 **Ghidra 12.1.4 본체와 Temurin Java 21.0.13+9**를 함께 사용합니다.

> `bin/sample.dll`을 실행하지 말고 Ghidra로 분석해 주세요. 함수 목록을 확인하고, 통신 초기화와 관련된 함수의 의사코드·호출자·호출 대상을 조사해 주세요. 추정한 함수 이름과 확인한 근거를 구분해 주세요.

`ned_host_rea_ghidra`의 `functions`로 실제 함수 목록을 먼저 받습니다. 반환된 함수명·주소를 `procedure`로 지정해 `decompile`, `assembly`, `callers`, `callees`, `references`, `info`를 요청합니다. 같은 대화에서 대상 내용이 같으면 분석을 재사용하므로 매번 Ghidra를 처음부터 실행하지 않습니다. 대상 파일이 바뀌면 별도 분석이 필요합니다. 동시 보관은 두 대화까지이며, 새 분석이 필요하면 가장 오래된 임시 분석을 종료합니다. 이 경우 원래 대화에서도 다시 분석할 수 있습니다.

분석 대상은 프로젝트 안의 64 MiB 이하 일반 파일입니다. 지원 형식은 REA/Ghidra가 헤더에서 판별하는 실행 이미지입니다. 임의 raw 바이너리의 CPU·로드 주소 지정, 사용자 Ghidra 스크립트, 외부 확장 설치, 디버거·대상 실행은 노출하지 않습니다. 이런 정보가 필요한 펌웨어는 헤더가 있는 ELF 등 가능한 입력 형식을 먼저 확인하세요.

Ghidra는 프로젝트 원본 대신 Ned의 전용 임시 복사본을 분석합니다. 결과는 원본 코드 복원이 아니라 디컴파일 추정입니다. 최적화·심볼 제거·지원하지 않는 명령어·누락된 디버그 정보에 따라 함수명과 자료형을 정확히 복구하지 못할 수 있습니다. 분석 성공과 원본 코드 수준의 정확도는 구분해야 합니다.

처음 여는 대상에는 명령 실행 권한 정책을 적용합니다. `전체 권한`에서는 반복 승인 없이 진행합니다. 분석은 정적이며 대상 프로그램을 실행하지 않습니다. Java 21 전용 네트워크 가드는 Ghidra JVM의 외부 DNS·소켓 접근을 차단하고 REA 통신에 필요한 루프백만 허용합니다. 이는 일반 프로그램 전체를 제한하는 OS 샌드박스와는 별개입니다.

Ghidra와 Java 때문에 설치 용량이 증가합니다. 별도 다운로드 없이 폐쇄망에서 분석하려면 필요한 구성입니다. 개발용 `jmods`·Java 소스 ZIP, 별도 Ghidra 문서·선택 확장 ZIP과 다른 OS의 실행 파일은 설치하지 않되, Ghidra 실행·스크립트 컴파일에 필요한 JDK 모듈과 라이선스는 유지합니다. 대응 소스는 반입 TGZ의 `source/`에 함께 제공합니다.

## 전체 권한에서 프로젝트 밖의 자료 읽기

> `D:\Reference\interface.md`를 읽고 현재 프로젝트의 통신 구현과 비교해 주세요. 외부 파일은 수정하지 마세요.

`read_external_file`은 절대 경로로 지정한 로컬 UTF-8 텍스트 파일을 최대 2 MiB까지 읽습니다. `list_external_directory`는 한 폴더의 목록을 최대 1,000개까지 비재귀 조회합니다. 두 도구 모두 `전체 권한`에서만 사용할 수 있으며, 권한을 낮추면 이후 읽기는 차단합니다.

외부 파일 생성·수정·삭제, UNC 네트워크 경로, 장치 경로와 대체 데이터 스트림은 지원하지 않습니다. Ned 실행 키와 내부 자격증명이 있는 앱 관리 경로도 모델 읽기에 노출하지 않습니다. 필요한 대상을 구체적으로 지정하면 넓은 디스크 전체를 불필요하게 읽지 않고 참조 자료를 활용할 수 있습니다.
