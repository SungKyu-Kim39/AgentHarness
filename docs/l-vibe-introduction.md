# L-Vibe 소개

**폐쇄망 개발 환경에서 자연어로 코드를 이해하고, 변경하고, 개발 지식을 활용하는 AI 개발 도구**

개발 업무에는 코드를 작성하는 시간만 필요한 것이 아니다. 기존 구현을 파악하고, 관련 파일을 찾으며, 변경의 영향을 검토하고, 그 결과를 문서로 남기는 과정에도 많은 노력이 든다. 특히 오랫동안 유지해 온 소프트웨어는 코드와 문서, 담당자의 경험이 여러 곳에 나뉘어 있어 작은 수정에도 상당한 사전 조사가 필요하다.

L-Vibe는 이러한 개발 과정을 사내 AI와 함께 수행하기 위해 만든 바이브 코딩 도구이다. 외부 인터넷 이용이 제한된 환경에서 사내 모델 서버와 프로젝트 코드를 연결하고, 대화를 실제 분석과 수정 제안으로 이어 주는 것을 목적으로 한다.

## 1. L-Vibe가 만들어진 목적

일반적인 AI 채팅에서는 개발자가 필요한 코드를 직접 찾아 복사하고, 답변을 다시 편집기에 옮겨 반영해야 한다. 관련 파일이 늘어날수록 설명을 반복하게 되고, 답변이 실제 프로젝트 구조와 맞는지 확인하는 부담도 커진다.

L-Vibe는 AI가 사용자가 선택한 프로젝트의 파일을 도구로 읽고 검색하도록 연결한다. 개발자는 원하는 결과와 제약 조건을 자연어로 설명하고, AI가 조사한 근거와 변경 제안을 같은 작업 흐름에서 검토할 수 있다. 코드 설명, 기능 구현, 오류 원인 조사, 리팩터링, 개발 문서 작성이 서로 단절되지 않도록 돕는 것이 핵심이다.

여기서 바이브 코딩은 자연어로 의도를 전달하고 구현을 점진적으로 구체화하는 개발 방식을 뜻한다. L-Vibe는 이 과정에 프로젝트 탐색, 변경 승인, 도구 실행 근거 확인을 결합한다. 개발자는 목적과 판단 기준을 제시하고 결과를 검토하며, AI는 조사와 초안 작성, 반복적인 정리 작업을 보조한다.

## 2. 대화에서 프로젝트 작업으로 이어지는 사용 흐름

기본적인 사용 방법은 프로젝트 폴더를 선택한 뒤 필요한 작업을 대화로 요청하는 것이다. 처음부터 정교한 프롬프트나 모든 도구의 사용법을 익힐 필요는 없다. 원하는 결과, 대상 범위, 유지해야 할 동작을 구체적으로 설명하는 것부터 시작할 수 있다.

예를 들어 다음과 같이 요청할 수 있다.

> 이 프로젝트의 주요 모듈과 진입점을 조사하고, 처음 참여하는 개발자가 읽을 수 있는 구조 설명서를 작성하라.

> 이 함수에서 오류가 발생할 수 있는 경로를 조사하고, 기존 동작을 유지하는 수정안을 제시하라.

> 이 모듈의 Windows 이식 방안을 검토하라. 기존 VxWorks 지원을 유지해야 하며, 플랫폼에 종속된 부분과 추가 확인이 필요한 사항을 구분하라.

L-Vibe는 OpenCode Desktop을 기반으로 대화, 프로젝트, 세션, 파일 탐색, 모델 선택과 도구 이벤트를 제공한다. 사용자는 AI의 설명뿐 아니라 어떤 도구가 어떤 대상을 조사했는지도 확인할 수 있다. 파일 수정은 제안을 검토하고 승인하는 흐름으로 진행하며, 승인 시점에 대상 내용이 달라졌다면 충돌을 확인한다.

사용성이 지향하는 바는 개발자가 여러 도구 사이에서 자료를 옮기는 부담을 줄이는 것이다. 기존 코드와 요구사항을 조사한 내용이 구현 제안과 문서 작성의 근거로 이어지고, 개발자는 필요한 지점에서 방향을 조정할 수 있다.

## 3. 폐쇄망 환경을 고려한 설치와 모델 선택

L-Vibe는 Windows 10·11 x64 환경을 대상으로 구성한 설치형 소프트웨어이다. 반입 이후 구성 요소를 추가로 내려받기 어려운 조건을 고려하여, 필요한 런타임과 도구, 기본 스킬을 배포 묶음에 포함한다.

처음 사용하는 흐름은 다음과 같다.

1. 반입한 TGZ 파일의 압축을 해제한다.
2. 포함된 EXE로 L-Vibe를 일반 사용자 계정에 설치한다.
3. 설정 JSON에 사내 모델 API 주소, 인증 키와 모델 ID를 입력한다.
4. L-Vibe를 실행하고 프로젝트와 모델을 선택한다.

직원 PC에서 npm이나 pip로 구성 요소를 설치하는 절차를 요구하지 않는다. 모델 가중치는 설치 파일에 포함하지 않으며, 실제 답변 생성과 임베딩에는 설정한 사내 모델 API를 사용한다.

여러 LLM의 주소와 키를 등록하고 모델을 선택할 수 있다. 모델별 컨텍스트와 출력 토큰 한도도 사내 서버의 실제 지원 범위에 맞추어 지정할 수 있다. 임베딩 모델은 LLM과 별도로 한 개를 설정한다.

저장된 설정이 있는 경우에는 기존 값을 유지한다. 이후 설정을 바꾸려면 알림 영역의 L-Vibe 메뉴에서 편집한 JSON을 명시적으로 가져온다. 설정한 API 키는 Windows 사용자 보호 기능을 이용하여 암호화 저장한다.

## 4. L-Vibe의 구성과 각 요소의 역할

L-Vibe는 공식 OpenCode Desktop과 엔진을 기반으로 사내 모델 연결, 승인 중계, 로컬 분석 도구와 지식 저장 기능을 결합한 배포판이다. 개발자가 각 구성 요소를 따로 설치하고 연결하는 수고를 줄이도록 구성하였다.

| 구성 | 역할 | 업무에서의 활용 |
|---|---|---|
| OpenCode Desktop 기반 화면과 전용 엔진 | 대화·세션·프로젝트 작업 및 도구 호출 관리 | 요청부터 분석과 변경 검토까지 하나의 작업 흐름 제공 |
| 사내 모델 연결 계층 | 설정한 LLM에 요청을 전달하고 모델 선택 지원 | 업무 특성에 맞는 사내 모델 활용 |
| 호스트 도구와 승인 중계 | 프로젝트 접근 범위, 파일 변경 승인과 충돌 확인 | 수정 대상과 내용을 검토하며 작업 진행 |
| 기본 스킬 34개 | 요구사항 정리, 계획, 디버깅, 리뷰, 보안, 문서와 데이터 분석 등의 작업 지침 제공 | 반복적으로 필요한 개발 절차와 검토 관점 활용 |
| Aegis·Conductor 어댑터 | 방법론 지침과 기존 작업 트랙 문서를 개발 도구에 연결 | 큰 작업의 계획·진행·검증 근거 정리 |
| Serena·clangd | C/C++ 심볼 정의·참조 등 의미 탐색 | 기존 코드의 구조와 변경 관련 지점 조사 |
| Graphify·REA | 로컬 코드의 AST 구조 분석과 지원 대상 산출물의 제한된 정적 분석 | 소스 관계 및 일부 레거시 산출물 조사 보조 |
| Git·문서·브라우저·데이터 MCP | 변경 이력, 문서 내용, 로컬 웹 화면과 데이터 조회 | 코드 주변의 개발 자료를 함께 검토 |
| OpenViking | 로컬 지식 저장 및 사내 임베딩 기반 검색 | 명시적으로 색인한 프로젝트 자료 재검색 |

기본 스킬은 작업 방법을 안내하는 문서이며, MCP는 AI가 실제 도구를 호출하기 위한 연결 방식이다. 두 요소를 함께 사용하면 작업을 어떻게 수행할지에 대한 지침과 실제 프로젝트를 조사하는 수단을 연결할 수 있다. 스킬이 포함되어 있다는 사실만으로 해당 테스트나 검토가 실행된 것은 아니며, 완료 여부는 실제 도구 결과로 확인한다.

기본 탑재 MCP 6종은 Serena, Git, Playwright, MarkItDown, Chrome DevTools, DuckDB Local이다. 이들 도구는 L-Vibe가 제공하는 범위로 제한하여 연결한다. 예를 들어 문서는 텍스트 변환과 읽기, 데이터는 선택한 로컬 파일에 대한 조회, 브라우저는 허용한 로컬 개발 페이지의 관찰과 진단에 활용한다. 원본 도구의 모든 기능을 그대로 노출하는 구성은 아니다.

## 5. OpenViking을 통한 개발 지식 활용

프로젝트가 커질수록 필요한 정보는 코드만으로 설명되지 않는다. 설계 의도, 인터페이스 정의, 오류 대응 기록과 운영상의 제약도 함께 찾아야 한다. OpenViking은 이러한 자료 중 사용자가 명시적으로 선택하여 색인한 내용을 다시 검색하는 데 활용한다.

L-Vibe의 OpenViking은 앱과 함께 시작하고 종료하는 로컬 서비스이다. 지식 데이터는 사용자 데이터 폴더에 보관하며, 임베딩 계산에는 JSON에 지정한 사내 API를 이용한다. 기본 스킬도 로컬 OpenViking skills에 자동 등록하도록 구성되어 있으며, 실제 등록 완료 상태는 알림 영역의 메뉴에서 확인할 수 있다.

기존 OpenViking에 축적한 개인 기억과 자료도 명시적인 내보내기·가져오기를 통해 재활용할 수 있다. 가져온 개인 지식은 해당 사용자의 모든 프로젝트에서 읽기 전용으로 검색한다. 대화 기록은 L-Vibe 채팅 세션으로 자동 변환하지 않으며, 새 대화를 기억으로 자동 업로드하지 않는다.

프로젝트 파일의 색인은 사용자 승인을 거친다. 개인 대화나 프로젝트 전체를 자동으로 공용 지식에 업로드하는 방식은 사용하지 않는다. 또한 일반 LLM 대화가 성공한 것과 OpenViking의 등록·색인·검색이 성공한 것은 각각 확인해야 한다.

활용을 시작할 때에는 작은 개발 문서 한 개를 색인하고, 해당 문서의 내용을 검색하여 실제 결과를 확인하는 방법이 적합하다. 이후 필요한 자료를 선별하여 지식 범위를 넓혀 갈 수 있다.

## 6. 업무에서 기대할 수 있는 효용

### 기존 코드 이해와 신규 담당자 적응

파일과 모듈의 역할을 조사하고, 주요 처리 흐름을 설명하며, 관련 문서의 초안을 작성하는 데 활용할 수 있다. 처음 접하는 코드에서 어디부터 살펴보아야 하는지 판단하는 부담을 줄이고, 조사 결과를 팀에서 검토할 수 있는 형태로 정리하는 데 도움이 된다.

### 오류 조사와 변경 검토

오류 증상과 관련 코드를 함께 검토하고, 원인 가설과 확인해야 할 지점을 정리할 수 있다. 수정 제안의 근거와 영향 범위를 확인하면서 진행하므로, 개발자가 최종 판단에 집중하기 쉽다. 실제 실행 결과가 없는 경우에는 가설과 검증된 사실을 구분하여 검토한다.

### 레거시 개선과 플랫폼 이식

플랫폼 종속 코드, 중복된 구현, 복잡한 오류 처리 등을 조사하고 개선 단계를 나누는 데 활용할 수 있다. C/C++ 의미 분석은 실제 컴파일 옵션과 include 경로, SDK의 제공 여부에 영향을 받으므로, 프로젝트 환경을 함께 준비할수록 유용하다.

### 개발 문서와 작업 인계

구현 내용을 바탕으로 설계 설명, API 문서, 변경 요약과 인계 문서를 작성할 수 있다. 코드 조사와 문서 초안 작성을 같은 작업 흐름에서 수행함으로써, 개발 중 확인한 내용을 다시 정리하는 부담을 줄일 수 있다.

### 웹 화면과 데이터 검토

로컬 웹 페이지의 접근성 구조와 콘솔 오류를 확인하고, 지원하는 로컬 데이터 파일을 조회하는 작업에도 활용할 수 있다. UI 품질, 접근성, 데이터 검증과 통계 해석에 관한 기본 스킬을 함께 사용하여 검토 관점을 보완할 수 있다.

이러한 효용은 프로젝트의 준비 상태와 모델 성능, 요청의 구체성에 따라 달라진다. 실제 적용에서는 작은 과제부터 사용하고, 조사 시간과 수정 검토 부담이 어떻게 달라지는지 업무 사례로 확인하는 것이 바람직하다.

## 7. 작은 개발 과제부터 시작하는 활용 제안

첫 활용 대상으로는 익숙한 모듈의 구조 설명, 짧은 함수의 오류 처리 검토, README 보완과 같이 결과를 직접 판단하기 쉬운 과제가 적합하다. 요청할 때에는 다음 세 가지를 함께 전달하면 도움이 된다.

- **목적:** 무엇을 해결하거나 만들려는지 설명한다.
- **범위와 제약:** 대상 파일, 유지해야 할 동작과 변경해서는 안 되는 조건을 지정한다.
- **완료 기준:** 원하는 산출물과 확인 방법을 제시한다.

예를 들면 다음과 같다.

> 통신 모듈의 오류 처리를 검토하라. 공개 인터페이스와 정상 처리 동작은 유지하라. 먼저 관련 코드를 조사한 뒤 수정안을 제시하고, 별도로 실행해야 할 테스트 항목을 정리하라.

작업의 범위를 좁혀 실제 결과를 확인하는 경험이 쌓이면, 여러 파일의 변경이나 기존 프로젝트의 구조 개선으로 활용 범위를 넓힐 수 있다. 팀에서 유용했던 요청 방식과 검토 기준을 문서로 남기면 다음 작업자의 시작점으로도 활용할 수 있다.

## 8. 현재 제공 범위와 활용 시점

이 글은 L-Vibe 0.2.6의 구현 범위를 기준으로 작성하였다. 현재 버전은 검증 후보이며, Windows 환경과 실제 사내 모델·SDK를 대상으로 한 전체 수용 검증은 계속 진행하는 단계이다. 일반 명령 실행은 제공하지 않으므로 빌드와 테스트는 기존 개발 환경에서 수행하고 결과를 확인해야 한다. 새 Desktop의 반복 출력 대응, 답변 재출력과 세션 전체 변경 비교 등은 후속 구현 범위이다.

따라서 현재는 코드 이해, 수정 제안과 승인, 문서 작성 및 지원하는 로컬 도구의 활용부터 시작하는 것이 적합하다. AI가 제시한 계획과 실제 수행 결과를 구분하고, 기존 코드 리뷰와 검증 절차에 결과를 연결하여 사용하는 것이 중요하다.

L-Vibe가 지향하는 효용은 개발자가 사내의 코드와 자료를 바탕으로 더 빠르게 조사하고, 더 구체적으로 판단하며, 필요한 변경을 검토할 수 있도록 돕는 데 있다. 반복적인 조사와 정리 작업부터 L-Vibe를 활용하여, 개발자가 설계와 문제 해결에 집중할 수 있는 작업 방식을 마련하고자 한다.
