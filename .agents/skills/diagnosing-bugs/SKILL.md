# Diagnosing Bugs — Ned development

Matt Pocock diagnosing-bugs의 피드백 루프를 이 프로젝트에 적용한다. ../../README.md와 references/upstream.md에 출처가 있다.

1. 사용자 증상, 설치 버전·수정 패치, OS, 실행 단계와 기존 진단 결과를 확인한다. 모르는 사실을 원인으로 단정하지 않는다.
2. 실제 증상을 검출하는 가장 작은 피드백 루프를 만든다. 기존 대상 테스트, 입력 fixture, CLI, 합성 서버, 프로세스 수명·종료 코드, GUI 관찰 순으로 적절한 경계를 선택한다. 단순 import 성공을 대화·도구·GUI 동작 성공으로 대체하지 않는다.
3. 원래 결함이나 검증된 재현 조건에서 루프가 실패하는지 확인한다. 다른 원인의 실패를 원래 문제의 재현으로 기록하지 않는다.
4. 근거가 있는 가설과 이를 구분하는 예측을 짧게 정리한다. 한 번에 한 변수를 바꾸고 관찰 결과로 가설을 갱신한다. 명확한 단일 원인이 보이면 억지로 여러 가설을 만들지 않는다.
5. 재현을 유지하는 최소 수정 후 같은 루프와 관련 회귀 검증을 실행한다. 테스트를 추가할 때는 실제 결함을 검출하는 경계를 사용한다.
6. 임시 계측과 본 작업 소유 프로세스·파일을 정리하고, 원인·수정·실행한 검증·남은 제한을 설명한다. 사용자 앱이나 작업을 강제 종료하지 않는다.

## 환경과 민감 정보

실제 Windows/사내 서버가 없으면 읽기 전용 코드 조사와 독립 fixture 검증은 계속한다. 가설과 검증 사실을 구분하고, 사용자에게 필요한 경우에만 작은 진단을 요청한다. 원문 로그·요청 본문·키를 수집하는 범용 덤프 대신 고정 상태·종료 코드·오류 위치 등 최소 정보만 사용한다.

사내 Qwen의 긴 대기는 장애로 단정하지 않는다. 생성 대기에 기본 시간 제한을 추가하거나 취소·파일 쓰기 같은 부작용을 자동 반복하지 않는다. 합성 부하 루프는 자원과 횟수를 제한하며 사용자 서버에 무작위 대량 요청을 보내지 않는다.

원본의 HITL 셸 템플릿이나 프로덕션 계측을 자동 설치하지 않는다. 재현 환경이 없다는 이유로 전체 작업을 중단하거나 동일 질문을 반복하지 않는다.
